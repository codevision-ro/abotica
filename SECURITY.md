# Security Policy

## Reporting a vulnerability

Please do not open a public issue for security problems.

Report vulnerabilities privately through GitHub: open the repository's **Security** tab and choose **Report a vulnerability** (private vulnerability reporting / security advisories). Include what is affected, how to reproduce it and the impact you expect. You will get a reply in the advisory thread, and the fix will be coordinated there before anything is disclosed publicly.

## Supported versions

Only the latest release is supported. Fixes are not backported: update with `install.sh` (see [DEPLOY.md](DEPLOY.md)).

## Security model

Knowing these assumptions helps decide what counts as a vulnerability.

- **Single user.** One account per instance. Sign-up is open only while no account exists and `ALLOW_SIGNUP` is not `false`. When `SETUP_CODE` is set (`install.sh` sets it), creating the account also needs that code, compared in constant time, so whoever reaches a new server first cannot claim it. Login supports TOTP 2FA.
- **Secrets.** API keys and tokens saved from the UI are encrypted in Postgres with AES-256-GCM using `VAULT_KEY`. Anyone with `VAULT_KEY` and database access can read them; losing `VAULT_KEY` makes them unreadable. A secret is global or bound to one project: an MCP server started by a run gets, through `{{secret:NAME}}`, only the global secrets and those of the run's project, and a reference to another project's secret fails. Placeholders read the vault only, never the worker's environment; tests the user starts from the MCP registry may use every secret. The environment variables, headers and OAuth client secret saved on an MCP server are encrypted the same way.
- **Agent commands and stdio MCP servers run in a sandbox:** a Docker container per workspace (commands run as an unprivileged user without capabilities; memory, CPU and process limits; gVisor when installed) on an internal network. Agents allowed to run commands as root get, for those commands only, the capabilities package installs need (CHOWN, DAC_OVERRIDE, FOWNER, FSETID, SETUID, SETGID); `no-new-privileges` keeps the unprivileged user from becoming root through setuid binaries. Use gVisor on servers: root inside a runc container is one kernel bug away from the host. Without Docker there is no sandbox and nothing runs. The process sees only its workspace, gets an environment without the worker's variables, and reaches the network only through a proxy that applies the workspace's policy (off, package registries, chosen domains, or any public host) and always refuses private, loopback, link-local and cloud metadata addresses. Secrets stay out of workspaces; a stdio MCP server gets only the variables configured on it. Sandboxed stdio MCP servers run as a separate user from agent commands, so a command cannot read a server's environment, memory or private files. In a run's workspace a server never starts in the workspace: its working folder is `/opt/abotica/mcp/out/<server>`, outside the workspace volume, which agent commands can read but not change, so nothing an agent plants in the workspace (`.npmrc`, `pyproject.toml`, `node_modules`, links) is picked up by the server; the server can read the workspace files agents leave readable but cannot write there. All MCP servers that run in the same workspace share that one user, so they can read each other's environment (including secrets) and private files and use each other's network access: treat the servers running in one workspace as one trust domain. A server's own workspace is separate per server and secret scope (global, or each project). An agent allowed to run commands as root can still reach the MCP processes and files of its own workspace.
- **What the sandbox does not stop.** A policy that allows a domain allows sending data to it, and HTTPS is not inspected, so domain fronting through an allowed host is possible. Treat content agents read (web pages, files, emails) as untrusted: prompt injection can make an agent misuse whatever its tools and network policy allow. Text from outside reaches the model between `<untrusted-data>` tags: webhook payloads and task outputs that start trigger runs, the outputs and errors of delegated tasks in the report their delegator gets, pages from `web_fetch`, the text results of every MCP server and knowledge saved from a URL. The system prompt tells agents never to follow instructions found in those blocks, and look-alikes of the tags inside the data are removed so it cannot close its block early. This marking is a mitigation, not a boundary: a model can still be talked into following what it reads, so tool permissions, approvals and network policies are what limit the damage. Workspaces on the Docker network can reach each other if one listens on a port. Workspace volumes and folders have no disk quota, so an agent can fill the disk they live on.
- **The worker can control Docker.** In the Docker deployment the worker talks to the Engine API through `docker-socket-proxy`, limited to containers, exec, images, networks and volumes. That is still enough to start a privileged container, so a compromised worker means a compromised host. Nothing else can reach the proxy.
- **Pages agents fetch.** `web_fetch` and knowledge URLs are fetched by the worker, so they refuse private, loopback, link-local and cloud metadata addresses. The address is checked when the connection is made (a DNS answer that changes after the check cannot redirect it), every redirect is checked again, and response bodies are capped.
- **Bundled MCP servers.** They are offered to every agent until you disable them or an agent's permissions turn them off. Parallel Search and Context7 are third-party services: what an agent searches for or asks about leaves the instance. Playwright and Scrapling run in the agent's workspace with their own network policy (any public host), so an agent whose workspace network is off can still browse with them; the pages they load are untrusted content. Their tools start from the hints they declare (see Tool approvals), except Playwright's: browsing is clicks and typing, which it declares destructive, so all its tools start allowed. Its browser runs in the sandbox with a fresh profile per run; set the Playwright server to ask in an agent's permissions to approve each step.
- **Unsandboxed MCP servers.** A stdio MCP server with **Run in the sandbox** turned off runs directly in the worker with the worker user's files (not its environment variables). Use it only for servers you trust. Do not run the worker or the web app as `root`; use a dedicated user.
- **Previews.** What agents publish or start is served by the worker, each preview on its own subdomain of `PREVIEW_URL` named by 128 random bits, so a preview's scripts run on an origin separate from the app and from other previews. A private preview opens only through the app: with the user's session it issues a ticket bound to the preview, valid for a minute and usable once, which the preview host trades for its own signed cookie (`__Host-` over HTTPS); the app's session never reaches a preview host. A public preview needs only its link. Static previews are copies with regular files only (no links, nothing outside the published folder); live previews reach only the container and port stored for them. Previews expire on their own (live after 24 hours, static after 7 days) and can be taken down at once. Because a subdomain is the same site as the app, the app refuses requests that change something unless they come from its own pages (`Sec-Fetch-Site` and `Origin`), its auth cookies are `__Host-` over HTTPS, and stored files are not embeddable by other origins. A separate domain for previews gives the strongest isolation.
- **Tool approvals.** Each agent has an allowlist of tools and a list of tools that need human approval before they run. An MCP tool the agent's permissions do not cover (no entry for the tool, its server or "Default for MCP servers") starts from the hints its server declares: read-only and non-destructive tools run, the others (destructive tools and tools without hints) wait for approval, which also stops a scheduled or webhook run at that call until someone answers. Hints come from the server and are not trusted: they only choose that starting value, so a server can at most let its tools run without approval, never past a setting of the user. Approvals are answered from the web app or with Telegram buttons; creating a new agent always requires approval, and so do schedules and triggers an agent creates (they start runs later, without anyone watching). An automation runs an agent in a project only while that agent is on the project's team: this is checked each time it fires, so a trigger without a project does not reach into projects whose team the agent is not on. The kill switch stops all running agents.
- **Telegram.** The bot ignores everyone not listed in `TELEGRAM_ALLOWED_USER_IDS`; in a private chat it only replies with their user ID.
- **Webhooks.** A trigger's webhook URL carries a random token (24 random bytes); treat the URL as a secret, since by default it is all a caller needs to start runs. A trigger starts runs for at most 30 requests a minute (counted in Redis) and answers more with 429 and `Retry-After`: without a signing secret every request counts, with one only verified requests do, so someone who has only the URL can neither start runs nor use up the real sender's quota. Requests that fail verification have a separate limit of 120 a minute per trigger, above which they are answered with 429 and no longer logged one by one; verified requests are still accepted meanwhile. A trigger can also require signed requests: its signing secret is generated by the app (32 random bytes), stored encrypted with `VAULT_KEY` and shown once. Requests are checked against the raw body with a constant-time comparison, using Standard Webhooks (`webhook-id`, `webhook-timestamp`, `webhook-signature`; timestamps more than 5 minutes off are refused and each `webhook-id` is accepted once per trigger) or GitHub's `X-Hub-Signature-256`. GitHub signatures carry no timestamp, so a captured GitHub request can be replayed: the rate limit still applies, but prefer Standard Webhooks when the sender supports it. Refused requests are written to the audit log with the reason; a burst over either limit is logged once per minute.
